# 单周期 Verilog 加入异常与中断处理

> [!Note] 
> 
> 本次 P5X 实现的是异常处理，暂不涉及外部硬件中断

接下来，我们就需要为我们的小小 `CPU` 引入 “异常与中断处理” 机制。我们之前的 CPU 会一路往前跑，哪怕指令错误了也不给任何现象，导致可能会出现各种神秘的错误，那么在经过这一轮的改进以后，CPU 就能处理各种异常或是中断，完成自救。

很多同学刚看到指导书上一大堆异常码和 `CP0` 寄存器时可能会觉得头大，不知道从哪下手。其实只要我们顺着一条指令在 `CPU` 里流动的生命周期（取指 $\rightarrow$ 译码 $\rightarrow$ 执行 $\rightarrow$ 访存 $\rightarrow$ 写回/跳转），一步步思考“**每个阶段可能会出什么错？出了错该怎么上报？上报之后怎么跳转和恢复？**”，整个异常系统的设计就会变得非常自然。

在动工之前，还是希望你能看完每一小节，彻底弄清楚数据的传递链路之后再来独立完成 `P5X` ，毕竟你也不想一直卡在 `P5X` 看着别人超过你吧，值得注意的是，并没有什么往年题来练手，所以建议大家手搓一下 `CPU` 来获得更好的理解。下面我就顺着数据通路的推进过程，带大家一步步把这个异常系统搭出来。

---

## 取指阶段的防呆检测：IM

我们先从指令生命周期的第一站——取指阶段开始思考。在之前的 `CPU` 里，`PC` 给什么地址，`IM` 就老老实实吐出什么指令。但在引入异常机制后，我们首先得解决一个问题：**万一 `PC` 传过来的地址本身就是非法的呢？**

为了抓出这种非法的取指操作，我们需要在 `IM` 模块新增一个 `1` 位的输出端口 `AdELIM`，专门用来指示取指的 `PC` 是否合规。

那么，什么样的 `PC` 地址才算合规呢？这里有 `3` 条判定标准：

1. **地址必须按 `4` 字节对齐**：因为 `MIPS` 指令都是 `32` 位（`4` 字节）的，所以合法地址的最低两位 `PC[1:0]` 必须为 `2'b00`；


2. **地址不能超过上界**：即不能大于 `32'h0000_6ffc`；


3. **地址不能低于下界**：即不能小于指令段的起始地址 `32'h0000_3000`。

只要 `PC` 违反了上面三条中的任意一条，我们就把 `AdELIM` 拉高为 `1` 进行报错。

不过光拉高报错信号还不够。试想一下，如果当前 `PC` 已经越界或者没对齐了，`IM` 却依然把读出来的错误机器码往后传，后面的 `Controller` 和 `ALU` 岂不是会跟着一起乱套？所以这里有一个很关键的保护操作：**一旦检测到读取了错误的 `PC` 地址，我们就直接把 `IM` 输出的指令填充为 `nop`（`32'h0000_0000`）**，从源头上掐断非法指令搞破坏的可能！

---

## 控制中枢的扩容：Controller

指令顺利从 `IM` 出来之后，就来到了 `Controller` 模块进行译码。

在这一阶段，我们要为 `CPU` 新增 `5` 条指令：`syscall`、`mfc0`、`mtc0`、`eret` 和 `nop`
首先是指令的识别。之前我们习惯了单纯靠最高 `6` 位的 `OpCode` 和最低 `6` 位的 `Funct` 来确定指令类型，但这次加入的 `mfc0` 和 `mtc0` 比较特殊——它们属于协处理器指令，`OpCode` 全都是 `6'b010000`，而区分它们俩的字段居然是 `Rs`（`mfc0` 的 `Rs` 为 `5'b00000`，`mtc0` 的 `Rs` 为 `5'b00100`），所以在译码时需要根据 `Rs` 进行遴选，同时我们还需要控制 `PC` 什么时候走异常分支，什么时候走正常分支，我们添加一个 `Req` 输入端口来进行控制，一旦置为 `1` 就直接强制路由到异常 `PC` 0x4180。

识别出指令之后，接下来就是控制信号了：**这几条新指令需要 `Controller` 提供哪些新的控制信号？** 在动笔写代码之前，一定要先把下面这 `5` 个新增输出端口的作用以及原有 NPC_Sel 的功能扩展想清楚：

* **`CP0Wr`**：表示 `CP0` 协处理器的写使能。当执行 `mtc0` 指令需要往 `CP0` 里的寄存器写数据时，将它置为 `1`；


* **`CP02Reg`**：控制 `GRF` 写入数据来源的选择信号。当执行 `mfc0` 指令时，我们需要从协处理器读取数据送进通用寄存器，这时候就要靠这个信号切换 `GRF` 写回端的 `MUX`；


* **`EXLClr`**：表示错误状态的清空信号。当异常处理结束、执行 `eret` 指令准备返回时，用它来通知 `CP0` 清空错误状态标记；


* **`Syscall`**：系统调用异常指示信号。遇到 `syscall` 指令时直接拉高（`syscall` 本身就是靠主动触发异常来实现系统调用的）；


* **`RI`**：未知/未定义指令（Reserved Instruction）异常指示信号。


* **`NPC_Sel`**：这里要根据 Req 的拉起与否，确定走正常分支或是异常分支

这里重点聊一下 `RI` 和 `nop` 的关系。回忆一下，我们在搭基础 `CPU` 的时候为了省事，往往不会单独去判断 `nop` 指令，而是把 `nop` 和所有未实现的指令混在一起——只要所有已知指令的译码信号全为 `0`，就默认它什么都不干（相当于 `nop`）。

但是在引入 `RI` 异常之后，这种偷懒的做法就行不通了！因为我们必须区分出“**真正的 `nop` 指令**”和“**未定义的非法指令**”。所以这次我们必须把 `nop`（这里根据指导书我们采用的设计是 `OpCode` 和 `Funct` 均为 `0`）单独拎出来验明正身；只有当一条指令既不属于已实现的合法指令集，又不是 `nop` 时，才将 `RI` 拉高为 `1`。

---

## 算术与地址溢出检测：ALU

译码完成、从 `GRF` 读出操作数之后，数据就进入了 `ALU` 模块。在异常机制下，`ALU` 除了负责日常计算，还得兼职抓捕“算术溢出”。

仔细分析一下，哪些指令会用到 `ALU` 的加减法并且害怕溢出呢？其实可以分为两类：一类是纯算术指令（如 `add`、`addi`、`sub`），另一类是借助 `ALU` 计算访存地址的指令（如 `lw` 和 `sw`）。由于课程指导书要求把这些异常区分开，我们需要在 `ALU` 新增 `3` 个输出端口：

* **`Overflow`**：表示算术指令本身的计算是否发生溢出；


* **`AdELALU`**：读取 ~~抖M~~(`DM`) 数据（如 `lw`）时，地址计算是否发生溢出；


* **`AdESALU`**：写入 `DM` 数据（如 `sw`）时，地址计算是否发生溢出。

那么在 `Verilog` 里怎么判断两个 `32` 位数加减后有没有溢出呢？这里我采取的做法很简单而朴素：**双符号位扩展法**。

我们将参与运算的两个 `32` 位 `operand` 先按照有符号数扩展至 `33` 位，然后再做加减法：

```verilog
wire [32:0] extA = {inputA[31], inputA};
wire [32:0] extB = {inputB[31], inputB};
wire [32:0] resAdd = extA + extB;
```

算完之后，只需要看结果的第 `33` 位（`resAdd[32]`）和第 `32` 位（`resAdd[31]`）是否相等即可：如果这两位不相等，就说明运算结果超出了 `32` 位有符号数的表示范围，发生了溢出！

> [!CAUTION]
>
> 注意不要忘记：**这三个溢出输出仅在对应的指令下才允许有输出**！
>
> 这和我们之前在 `P3` 处理控制信号时的经验准则是一脉相承的：新加信号千万不能干扰不需要它的指令。比如 `addu` 和 `addiu` 本来就是不考虑溢出的无符号加法，哪怕算出来第 `33` 位和第 `32` 位不同，也绝对不能拉高 `Overflow`；同理，`AdELALU` 只能在执行 `lw` 类指令时才有效，`AdESALU` 只能在执行 `sw` 类指令时才有效。如果忘了加指令类型的限制条件，跑普通指令时就会疯狂误报异常哦 ~
>
> 当然在我们目前的 `CPU` 中并没有 `addu` 和 `addiu` 但多注意一些总是好的嘛

## 内存访存的边界守卫：DM

如果一条 `lw` 或 `sw` 指令在 `ALU` 里算地址时没有发生溢出，接下来这个地址就会被送进 `DM` 模块进行访存。

这时候我们同样要问一句：没发生算术溢出的地址，对 `DM` 来说就一定合法吗？显然不一定！于是我们需要仿照 `IM` 的思路，在 `DM` 模块也新增两个异常指示输出：`AdELDM` 和 `AdESDM`，分别用来指示 `lw` 和 `sw` 的访存地址是否出现异常。

`DM` 的地址检查逻辑非常直接，只需要满足两条规矩：

1. **地址必须按 `4` 字节对齐**：即地址的低两位 `Addr[1:0]` 必须为 `0`；


2. **地址不能超过数据段上限**：即地址最大只能为 `32'h0000_2fff`，同样最小只能是 `0` 哦

只要访存地址不满足上述条件，就拉高 `AdELDM` 和 `AdESDM`（指令类型过滤位于 `ExcUnit`）

## 异常集中仲裁中心：ExcUnit

> 船新的模块！

经过前面的改造，我们在 `IM`、`Controller`、`ALU` 和 `DM` 里埋下了一大堆异常检测信号（`AdELIM`、`RI`、`Syscall`、`Overflow`、`AdELALU`、`AdESALU`、`AdELDM`、`AdESDM`）。

现在问题来了：一条指令在执行过程中，完全有可能同时触发多个异常信号（比如一条 `lw` 指令既在计算地址时发生了 `AdELALU` 溢出，算出来的地址送到 `DM` 后又触发了 `AdELDM` 越界）。而 `CP0` 协处理器每次只能接收一个 `5` 位的异常码 `ExcCodeIn`，这时候我们该听谁的？

当然这个模块并非是一定需要单独建的，你完全可以把这堆判断逻辑塞进顶层或者 `CP0` 里。但是我个人比较喜欢解耦的设计，我认为抽离出一个新的模块来专门干这件事，代码可读性和可扩展性都会好很多。

我们先来看一下 `ExcUnit` 的接口定义：

| 信号名   | 方向  | 位宽 | 描述                          |
| -------- | ----- | ---- | ----------------------------- |
| `AdELIM` | input | 1    | `IM` 访问地址异常指示（取指） |
| `AdELDM` | input | 1 | `DM` 访问地址异常指示（`lw`）|
| `AdESDM` | input | 1 | `DM` 写地址异常指示（`sw`）|
| `AdELALU` | input | 1 | `ALU` 地址计算异常指示（`lw`）|
| `AdESALU` | input | 1 | `ALU` 存储地址计算异常指示（`sw`）|
| `Overflow` | input | 1 | 算术溢出异常指示 |
| `Syscall` | input | 1 | 系统调用异常指示 |
| `RI` | input | 1 | 非法指令异常指示 |
| `type` | input | 6 | 指令类型信号 |
| `ExcCodeIn` | output | 5 | 异常码输出，送入 `CP0` 的 `ExcCodeIn` |

### 内部逻辑与优先级仲裁

`ExcUnit` 的核心工作只有一件事：

* 按照题目给出的异常码表，把对应的 `5` 位异常码赋给 `ExcCodeIn`，如果没有异常则输出 `0`

这里最需要注意的就是**仲裁顺序**！当多个异常同时出现时，我们必须严格按照指导书里的优先级顺序用 `if - else if` 进行判断：

* **第一优先级（取指阶段）**：先判断取指异常 `AdELIM`（毕竟连指令都没取对，后面的译码和执行全都是无效的）；
* **第二优先级（译码阶段）**：接着判断未定义指令 `RI` 再判断系统调用 `Syscall`；
* **第三优先级（访存阶段）**：再判断访存阶段中的 `AdELDM` / `AdESDM` 和地址计算溢出 `AdELALU` / `AdESALU`。
* **第四优先级（计算阶段）**：最后判断单独的算术溢出 `Overflow` ；


另外你可能会注意到，不管是 `AdELIM`、`AdELALU` 还是 `AdELDM`，它们最后生成的 `ExcCodeIn` 其实都是同一个异常码 `AdEL`（`5'd4`），之所以在前面把它们拆得这么细，就是为了在这里能清晰地处理优先级和指令条件呢！

## 核心总管：CP0 协处理器

> 船新的模块 +1！
>

当 `ExcUnit` 把异常码整理好之后，就该交给整个异常系统的核心——`CP0` 协处理器来拍板处理了。

我们先来梳理一下 `CP0` 的输入输出接口：

| 信号名 | 方向  | 位宽 | 描述     |
| ------ | ----- | ---- | -------- |
| `clk`  | input | 1    | 时钟信号 |
| `reset` | input | 1 | 复位信号 |
| `en` | input | 1 | 写使能信号（连接 `Controller` 的 `CP0Wr`）|
| `CP0Addr` | input | 5 | `CP0` 读写寄存器编号（接指令的 `rd` 字段） |
| `CP0In` | input | 32 | `CP0` 写数据（接 `GRF` 读出的 `RD2`） |
| `VPC` | input | 32 | 异常发生时的受害 `PC` |
| `ExcCodeIn` | input | 5 | 异常类型/异常码（来自 `ExcUnit`） |
| `EXLClr` | input | 1 | 清除 `EXL` 标志（来自 `Controller`） |
| `Req` | output | 1 | 最终确认的异常发生指示信号 |
| `EPCOut` | output | 32 | `EPC` 寄存器的值（送往 `NPC`） |
| `CP0Out` | output | 32 | 从 `CP0` 读出的寄存器值（用于 `mfc0`） |

### 内部逻辑拆解

`CP0` 内部主要维护着三个关键寄存器：`SR`（`12` 号状态寄存器）、`CAUSE`（`13` 号原因寄存器）和 `EPC`（`14` 号异常返回地址寄存器）。它的内部逻辑我们可以按以下四个部分来写：

1. **同步复位**：在 `reset` 有效时，把内部所有寄存器的初值全部赋为 `0`。
2. **异常响应判定**：当收到异常码时，`CP0` 一定会响应吗？

> 当目前已经处于错误状态（即 `SR` 寄存器中的 `EXL` 位为 `1`）时，处理器不应再响应下一个错误。

所以，只有当**当前没有处于异常状态（`!EXL`）且确实传入了异常**时，`CP0` 才会真正拉高输出的 `Req` 信号响应异常！一旦决定响应，在时钟上升沿到来时，我们需要同时做三件事：

* 把 `SR` 的 `EXL` 位设为 `1`（标记进入异常状态，防止异常套娃）；
* 把 `ExcCodeIn` 写入 `CAUSE[6:2]` 保存犯罪证据；
* 把受害指令的地址 `VPC` 写入 `EPC` 寄存器，以便处理完异常后能找回原路。

3. **错误状态清空**：当异常处理程序跑完、执行到最后一行的 `eret` 指令时，外部传入的 `EXLClr` 为 `1`，此时我们在时钟上升沿把 `SR` 中的 `EXL` 位清零，解除异常锁定状态。
4. **常规寄存器读写（`mfc0` / `mtc0`）**：读取逻辑很简单，直接用一个组合逻辑根据 `CP0Addr` 选择输出对应的寄存器值到 `CP0Out` 即可；而写入逻辑则是在写使能 `en` 有效时，根据 `CP0Addr` 将 `CP0In` 写入对应的寄存器。

> [!IMPORTANT]
>
> 这里有一个特别阴的点：在用 `mtc0` 向 `SR` 和 `CAUSE` 写入数据时，**必须是按位（按规定的有效位段）写入**，绝对不能图省事直接写成 `SR <= CP0In` 整字覆盖！即使是以前过了的学长代码在这里也不对，当时直接给我卡住了 😤 说明学校强测也不怎么样，哈哈哈哈
>
>
> 因为在评测数据里，可能会故意用 `mtc0` 往 `SR` 或 `CAUSE` 的未定义保留位写 `1`，而按照规范这些保留位必须恒为 `0`。如果你直接整字写入，后面再用 `mfc0` 读出来的时候就会把那些非法的 `1` 读出来，导致评测点挂掉！所以大家写的时候千万老老实实按位赋值（只写 `SR[1]` ）哦 ~
>

---

## 异常跳转与返回：NPC

最后，当 `CP0` 拍板决定响应异常（输出 `Req = 1`），或者异常处理完毕执行 `eret` 时，我们需要控制 `CPU` 跳到正确的地方去执行。这就轮到最后一块拼图——`NPC` 模块出场了！

我们在原本单周期 `NPC` 的基础上，新增一个 `32` 位的输入端口 `EPC`（连接 `CP0` 的 `EPCOut`），用来接收异常或中断处理完以后的返回地址。

接着在 `NPC` 内部的选择逻辑里，直接增加两条新的跳转分支：

1. **异常/中断入口跳转（`EPC1`）**：当收到 `Controller` 发来的异常跳转信号（`NPC_Sel`）时，说明当前遇到了中断 or 异常。直接把下一个周期的 `NPC` 送入异常处理程序的固定入口地址 `32'h0000_4180`
2. **异常返回跳转（`eret`）**：当译码出 `eret` 指令时，选择从 `CP0` 传过来的 `EPC` 输入作为下一个周期的 `PC` 值，精准跳回当初发生异常的地方继续执行! （值得注意的是，异常处理程序有可能会修改 `EPC` 的值，所以有可能不是原来的地方）

> 另外在顶层连线的时候还有一个小细节：一旦当前周期触发了异常（`Req == 1`），这周期正在执行的那条受害指令就已经作废了，所以千万记得把 `GRF` 和 `DM` 的写使能（`RegWrite` 和 `MemWrite`）在 `Req == 1` 时强行置 `0` 屏蔽掉，防止报错指令把脏数据写进寄存器或者内存里哦 ~
>

---

到这里，整个带异常与中断处理的 `CPU` 数据通路就彻底串起来了！其实只要把 `ExcUnit` 和 `CP0` 拆解清楚，你会发现加异常和我们之前在 `P3` / `P4` 加普通指令的流程几乎一模一样，祝大家都能顺利的一把过点！
